The helix is cumulative. Each operator contains every capacity below it. Here's what that means concretely in the database:

**NUL** — observe. Can encounter state without changing it. This is the ground capacity. Every operator above NUL can also observe.

**SIG** — observe + direct attention. SIG inherits NUL's capacity to encounter and adds the ability to select. It can point at a target. In the database, SIG presupposes NUL because you can't direct attention at something you haven't encountered. The engine uses SIG to route — but routing requires first seeing what's there.

**INS** — observe + direct attention + create enduring identity. INS inherits NUL (it encounters the key-space to know the target doesn't already exist) and SIG (it directs attention at the specific coordinate to mint). Then it does its own thing: create the anchor. Without NUL, INS couldn't check for duplicates. Without SIG, INS wouldn't know where to create. INS is the persistence threshold — everything below is ephemeral, everything from here up writes to the log.

**SEG** — observe + attend + instantiate + draw boundaries. SEG inherits INS because you can't partition what hasn't been instantiated. When SEG draws a boundary on a collection, it first encounters the collection (NUL), identifies which targets are inside it (SIG), confirms they exist (INS), then draws the line. In the database, SEG's partition metadata depends on the coordinate registry that INS maintains. SEG can also instantiate — when partitioning creates new subsets, those subsets may need new target coordinates, which SEG mints through its inherited INS capacity.

**CON** — observe + attend + instantiate + partition + connect across boundaries. CON inherits SEG because connection presupposes that the two things being connected are differentiated — boundaries must exist before you can reach across them. In the database, CON's adjacency index depends on SEG's partition awareness to know that the source and destination are in different parts of the key-space. CON also inherits INS — it can mint edge identities. And it inherits NUL — it observes both targets before connecting them. When CON adds an edge, it first encounters both endpoints (NUL), directs attention at them (SIG), confirms they exist (INS), recognizes they're in separate spaces (SEG), then creates the relationship.

**SYN** — all of the above + merge into emergent whole. SYN inherits CON because you can't merge things that aren't connected. In the database, SYN's alias resolution and edge merging depend on the CON graph to know what's connected to the targets being merged. SYN also uses SEG to dissolve the boundary between the two merging targets. And INS to mint the merged target's identity. When SYN merges two targets, it observes both (NUL), attends to them (SIG), confirms they exist (INS), recognizes their boundary (SEG), sees their connections (CON), then creates the merged entity with inherited edges and a new identity.

**DEF** — all of the above + establish what holds. DEF inherits everything because setting a value at a target presupposes: the target exists (INS), it's in a known region of the key-space (SEG), its relationships are known (CON, which determines dependencies for formula operands), and any prior merges are resolved (SYN, so DEF writes to the correct alias-resolved target). DEF is where the type registry activates — the operand type determines which storage backend gets used. DEF can also do everything below it: it can observe (NUL), attend (SIG), instantiate (INS — if DEF arrives on a target that doesn't exist yet, should it auto-instantiate?), partition (SEG), connect (CON — a formula DEF implicitly declares dependencies), and merge (SYN). In practice, DEF leans most heavily on CON — formula operands create dependency relationships that the recomputation engine walks.

**EVA** — all of the above + evaluate against terms. EVA inherits DEF because you can't evaluate without terms to evaluate against. DEF establishes what holds; EVA tests whether something satisfies it. In the database, EVA's computation pipeline depends on: DEF-stored function definitions (the formula), CON-stored dependency graphs (the inputs), SYN-resolved aliases (the correct targets), SEG-maintained boundaries (which targets are in the active set), INS-registered coordinates (the targets exist). EVA runs the formula, which requires reading state (NUL), finding the right targets (SIG), gathering inputs from across the graph (CON), respecting merge aliases (SYN), respecting partition boundaries (SEG). EVA is the most expensive operator precisely because it exercises every inherited capacity in a single operation.

**REC** — everything. REC inherits all eight prior capacities and adds frame restructuring. REC can observe, attend, instantiate, partition, connect, merge, define, and evaluate — and it wraps all of these in an atomic frame change. In the database, REC's sub-operations can be any combination of the other operators. A schema migration REC might contain DEFs (rename fields), SEGs (archive old structure), CONs (rewire relationships), EVAs (update resolution policies), and INS (create new schema targets). REC guarantees atomicity because it has the capacity to do everything the other operators do, and it does them as one indivisible unit.

The practical consequence for the database: the fold's operator dispatch isn't nine independent handlers. Each handler can call the handlers below it. REC calls DEF, EVA, SEG, CON. EVA calls through the CON graph and reads DEF-stored values. SYN calls CON operations to merge edges. CON calls INS to check existence. The helix is the call hierarchy.

This is also why the fold processes operators sequentially and not in parallel. An EVA that arrives before the CON that establishes its dependencies would fail. A DEF that arrives before the INS that creates its target would fail. The helix ordering isn't just a theoretical dependency — it's the order in which the fold must be able to resolve references. The fold trusts that events arrive in an order consistent with the helix because the producers (n8n, the application) emit them in dependency order. If they don't, the fold rejects the event — you can't DEF a target that hasn't been INS'd.
